#### NOTALLY-AND-OPT-01: Stop the two full backups at each process start
- **What**: Each process start makes two full backups that the user did not ask for. The backupsFolder collector changes the first previous value (null) to "", and folderChanged("", folder) then returns true. So each start runs scheduleAutoBackup plus createBackup(), which makes a full periodic zip. It also runs autoBackupOnSave(folder, pw, null), which makes a full export to NotallyX_AutoBackup.zip, even though backup on save is off by default. A process start can come from the launcher, a reminder alarm, boot, a widget update, or the hourly SyncWorker after Android stopped the cached process. Rotation keeps only maxBackups = 3 files, newest first. So the daily backups get deleted, and all 3 kept files can be from the last few hours. README.md:85 names this local backup as the defence against a server that deletes or replays data.
- **Where**: android/app/src/main/java/com/philkes/notallyx/NotallyXApplication.kt:120-129 (onCreate backupsFolder collector, `?: ""` at :123 and :128); :202-207 (folderChanged); :238-269 (checkUpdatePeriodicBackup, createBackup at :258); :271-287 (checkUpdateAutoBackupOnSave, null block at :273-281); :176-199 (backupPassword collector)
- **Change**: Remove `?: ""` at :123 and :128 so that null goes through. Both helpers already take String?. Also delete the `backupFolderBefore == null` block at :273-281 and keep only `if (!backupOnSave && folderChanged(...))`. Today that block is dead. Without `?: ""` it would become live and do the same work as the backupPassword collector at :176-199, which already makes the on-save backup at start when the file is missing.
- **Benefit**: Cold starts no longer make a full backup or an extra on-save export. The daily AutoBackupWorker is again the only periodic backup, so the 3 kept files cover 3 days. A fresh install still makes a backup at once (workInfos is empty), and so does a folder change (the second emission has before != null). Each cold start no longer writes the full DB plus all attachments twice (WAL checkpoint, DB copy, temp file, copy to target). The saving per start is twice the size of the user's data.
- **Evidence**: Preference.kt:93-96 withPrevious() = scan(null) + filterNotNull, so the first pair is (null, folder). EMPTY_PATH = "emptyPath" (NotallyXPreferences.kt:399), so folderChanged("", folder) returns true at :206. Defaults: folder = Android/media/<pkg>/backups (NotallyXPreferences.kt:156-166), PeriodicBackup(periodInDays = 1, maxBackups = 3) (PeriodicBackup.kt:27, asserted in NotallyXPreferencesBackupsTest:68), backupOnSave = false (:167-168). With these defaults, the branch at :251-259 runs with execute = true. The else branch at :282 calls autoBackupOnSave(..., null) -> exportAsZip (ExportExtensions.kt:211-214). Rotation: listZipFiles sorted by lastModified desc, then drop(maxBackups) (ExportExtensions.kt:141-155, AndroidExtensions.kt:509-517). isTestRunner() returns early at :91, so no unit test covers this. git blame: upstream import 55e801b4.
- **Safety**: This is upstream code (55e801b4), not from 0a92797c. The backup zip format, file names, password use, WorkManager unique name and all preference keys stay the same. Only the extra runs at process start go away.
- **Verification**: The perf lens confirmed the whole chain in code: withPrevious, EMPTY_PATH, the defaults, both branches and the rotation order. Not run on a device. To verify: force-stop and start the app 3 times, then count the files in Android/media/com.notallyxyz/backups. Today the count goes up at each start (up to 3). After the fix it must not change. No unit test covers onCreate.
- **Effort**: S. **Risk**: low. **Impact**: high. **Net lines**: about -9 (estimate).
- **Status**: approved

#### NOTALLY-AND-OPT-03: Replace zstd-jni with java.util.zip in CompressUtility
- **What**: zstd-jni is a native JNI library that ships for 4 ABIs. Only CompressUtility uses it. CompressUtility compresses in-memory undo snapshots (EditTextState) of notes longer than 10,000 characters. These snapshots never go to disk, the DB, a backup or the sync payload. The KDoc already says GZIP.
- **Where**: android/app/src/main/java/com/philkes/notallyx/utils/CompressUtility.kt:23-50 (compressTextAndSpans, decompressTextAndSpans); utils/changehistory/EditTextWithHistoryChange.kt:51-58, :127 (EditTextState); android/app/build.gradle.kts:392, :425; android/gradle/libs.versions.toml:45, :125
- **Change**: Compress with DeflaterOutputStream and Deflater(Deflater.BEST_SPEED). Call end() on the Deflater in finally. Decompress with InflaterInputStream in use {}. Catch errors in decompress and return ("", emptyList()), as CompressUtilityTest expects for invalid data. Remove the zstd-jni @aar dependency, the zstd-jni test dependency and the two catalog entries.
- **Benefit**: The APK and installed size drop by 2,499,796 B (-17%), or by 1,082,472 B after OPT-02. The app has one fewer native library in its process and one fewer third-party dependency.
- **Evidence**: grep: CompressUtility.kt is the only file that imports com.github.luben. The callers are EditTextState (EditTextWithHistoryChange.kt:55, :127) and two tests. ChangeHistory.kt keeps changes in an in-memory ArrayList (maxSize 1000). No parcel, bundle or save path touches EditTextState. unzip -lv: libzstd-jni-1.5.7-6.so is 603,960 (arm64) + 478,512 (armv7) + 691,236 (x86) + 726,088 (x86_64) B. apkanalyzer: com.github.luben dex is 4,476 B. git blame: upstream subtree.
- **Safety**: The compressed bytes exist only in RAM, so they are not a storage format. This is upstream editor code, not security-review code. No schema, preference key or crypto change.
- **Verification**: CompressUtilityTest and EditTextCompressionTest cover the round trip and the invalid-data case. For notes over 10k chars, each keystroke runs 2 compressions and 1 decompression on the main thread (UiExtensions.kt:368, 377, 385). Deflate level 1 is a bit slower than zstd level 4 and compresses a bit less, so the undo history of long notes uses a bit more RAM (estimate, not measured). Before release, type in a note of about 100 KB on a slow phone and check the latency.
- **Effort**: S. **Risk**: low. **Impact**: high. **Net lines**: about -3 (estimate).

#### NOTALLY-AND-OPT-06: Keep sync setup, Disconnect and Delete server data from stopping halfway or crashing
- **What**: Create account, Connect, Disconnect and Delete server data run in the Settings fragment's viewLifecycleOwner.lifecycleScope. A rotation, a dark-mode switch or leaving Settings cancels that coroutine, but the blocking HttpURLConnection request still completes on the server. ### Areas in good shape
- HTTP client: one transport for each account, TLS 1.2 or newer, no redirects, a timeout on each call. Bodies are closed and capped. Blobs stream to and from disk and are written atomically.
- Goroutines and timers: all engine work runs under one context and WaitGroup. Engine.Stop cancels and waits. reminderLoop stops on its channel. No leaks found.
- The long poll backs off from 5 s to 5 min on network errors. The server rate limiter counts only authentication failures.
- Save path: 600 ms editor debounce, 2 s sync debounce, unchanged notes skipped, 'changed' bursts combined (30 ms). Save errors show and retry.
- Cache: ApplyRemote and applyPending store the changes and the cursor in one bbolt transaction. The decrypted attachment cache has a 64 MiB limit. The disk cache stays sealed. Plaintext temp copies are removed on quit and at start.
- Frontend weight: no framework, no bundler, no third-party JS, no web fonts. About 112 KB of plain ES modules. Thumbnails load lazily.
- Packaging: Wails production builds strip symbols (-w -s) and CI adds -trimpath. The 4 direct Go dependencies are all needed.
- Tests: 'go test -race ./core/' runs the core, with end-to-end sync against the real server. StartLive has no test.
- UI basics: Undo toasts for archive and delete, confirmations for permanent actions, keyboard shortcuts in tooltips, aria labels on icon buttons, empty states, good list-editor keys.
- Security-review code (0a92797c body and blob limits, 413 branch), the reminder caps (466e12e2) and all seal, TLS and redirect handling stay untouched by every finding. Only NOTALLY-DESK-OPT-05 touches key handling: it changes the key-store call sites at app.go:105, :204 and :263.

#### NOTALLY-SRV-OPT-01: Cap the POST /v1/account request body at 64 KiB
- **What**: createAccount is the only endpoint that decodes a JSON body without a known account. tokenHash checks only the token format, so any random 32-byte token gets to decodeJSON. decodeJSON allows 32 MiB (maxRequestBytes). The decode runs before the Lookup and the signup check. The signup_disabled 403 and a decode 400/413 do not call limiter.fail, so the rate limiter does not block these requests. In Go 1.27 (JSON v2 is the default), Decode buffers the whole value and doubles the buffer when it is 75% full. A body of about 32 MiB gives a 64 MiB buffer, and Unmarshal copies the 32 MiB invite string. That is about 64 to 96 MiB of live heap per request (estimate). About 3 parallel requests can go past mem_limit 256m (GOMEMLIMIT 192MiB is only soft). The kernel then OOM-kills the server, and all long polls and uploads stop. ### Areas in good shape
- Long poll: the server registers the waiter before the read, stops the timer, handles client disconnect, and wakes all waiters on shutdown and DeleteAccount. No goroutine, ticker or polling loop runs per request.
- Changes copies record bytes out of the bbolt read transaction and encodes JSON after the transaction ends. A slow client does not hold a read transaction.
- The log bucket keeps one entry per record, so a pull costs O(changed records), not O(history).
- Blobs stream to disk through a LimitReader and stream out through http.ServeContent on *os.File (sendfile, Range). The server never holds blob bytes in memory.
- Apply is one bbolt transaction with a conflict check per record and the quota check inside. PutBlob checks existence and quota again inside the transaction.
- No panic paths: byte slices are length-checked before use, and auth always sets the context values.
- Timeouts are per handler (long poll, 30 min blobs) with ReadHeaderTimeout and MaxHeaderBytes. No server-wide ReadTimeout, which would cancel long polls.
- Bounded memory state: the limiter map is pruned once per window; the waiters map has at most one channel per account.
- Dependencies: only go.etcd.io/bbolt and golang.org/x/sys (indirect).
- Image: static -trimpath -s -w build on scratch. Dockerfile copies only top-level *.go, and .dockerignore keeps seal/, cmd/, tests and testvectors.json out.
- No dead endpoints: Android, macOS and desktop clients call all 11 routes. No over-abstraction: Store is concrete, handlers are one function each, the limiter is 51 lines.
- Caddy encode compresses the base64 JSON change pages and skips octet-stream blobs.
- Tests cover accounts, rate limit, conflicts, tombstones, paging, long poll, blobs and quota. CI runs go test -race before the image build.
- Security scope left alone on purpose: duplicated rate-limit and bearer parsing in createAccount and auth, GOMEMLIMIT in Dockerfile:15 and compose.yaml (0a92797c), seal/ and testvectors.json.
